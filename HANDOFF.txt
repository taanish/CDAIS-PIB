PART A — FOR YOUR BOSSES (plain language, no code)
--------------------------------------------------------------------------------

WHAT WE ARE DOING
  Building a systematic, searchable dataset of Indian government press releases
  (from the Press Information Bureau, PIB) to identify and catalogue every
  mention of the government deploying or using Artificial Intelligence — which
  system, which agency, which application domain, what stage (announced / piloted
  / operational). The end product is a structured table that a researcher can
  filter, count, and cite.

THE METHOD, IN ONE PARAGRAPH
  PIB's own website has an advanced search, but it silently caps results at 1,000
  per query and cannot do partial-word matching — so it would miss systems like
  "MausamGPT" (a weather chatbot) and give no way to know what it missed. Instead
  we downloaded the releases directly and search them on our own machine. This
  lets us (a) prove how complete our keyword coverage is — something the website
  can never tell you — and (b) find AI systems by naming patterns the website's
  search structurally cannot express. As a by-product we get a clean, complete
  PIB corpus that is itself a publishable research asset.

HOW THE KEYWORD METHOD WORKS (the core intellectual approach)
  Start with a seed list of AI terms. Search the corpus. Read what matched, and
  harvest adjacent vocabulary that signals AI use (e.g. the "-GPT" suffix, named
  systems like "IndiaAI" or "Bhashini"). Add those, search again, repeat until
  new terms stop surfacing new releases. A human reviews every proposed term, so
  the list never drifts into irrelevance. This is deliberately generous on
  inclusion — we would rather over-collect and filter later than miss a real
  deployment.

WHAT WE CAN CLAIM (the headline result so far)
  On a fully-downloaded test year (2025, 15,435 releases), the keyword method
  achieved an estimated 87–98% RECALL — i.e. it caught 87–98% of all genuinely
  AI-relevant releases — and it CONVERGED IN ONE ROUND (the second pass added
  under 1% new material). Crucially, this recall number is measurable ONLY
  because we have the complete year to check against. A website-search-only
  approach could never produce this figure. This is the single strongest
  methodological argument for the whole exercise.

WHAT IS DONE vs. WHAT REMAINS
  DONE:
    - Complete corpus for 2017–2026 (~100,000 releases), including every
      AI-dense recent year. Zero data-quality defects.
    - A validated 31-term AI vocabulary with a measured recall figure.
    - All infrastructure to search, expand, and (next) classify.
  REMAINS:
    - Three scope decisions (see Part E) — a research-judgement call, your call.
    - The classification pass: turning "mentions AI" into "deploys AI, here's
      the system and the evidence quote." This is the actual deliverable.
    - Finishing the pre-2017 tail of the download (low value; see below).

HONEST FRAMING OF DIRECTION
  The download of older years (2003–2016) is the LOW-VALUE tail: AI content there
  is nearly absent (the phrase "artificial intelligence" appears ~150 times in
  all of 2018 vs ~720 times in 2025). The research corpus we actually need —
  2017–2026 — is already complete. The remaining download runs unattended in the
  background and is not on the critical path. If PIB's servers (which have been
  intermittently down) never let it finish, the study is unaffected: we would
  report "complete for 2017–2026" and note the earlier partial coverage.

COST
  The download and search cost nothing but machine time — no paid API is
  involved. The only paid step is the final AI-classification pass over the
  ~2,400 candidate releases per year, estimated at roughly USD 200 for the
  highest-quality model on the full candidate set (much less with a cheaper
  model). Classification can be re-run cheaply as the definition of "AI
  deployment" is refined.

PART C — DATABASE SCHEMA (for querying corpus.db)
--------------------------------------------------------------------------------

The database has four conceptual layers:
  Layer 1  fetch_log            provenance — one row per relid ATTEMPTED
  Layer 2  releases             the corpus — parsed release records
           ministries           85-value controlled vocabulary (from PIB's form)
           releases_fts          full-text search index over releases
  Layer 3  terms, term_matches  the keyword-expansion vocabulary + matches
  Layer 4  ai_classifications   the research payload (EMPTY until classification)
           classification_runs
  Ops      crawl_sessions       one row per crawl run (bookkeeping)

Open it read-only (safe even while the crawler is writing):
  sqlite3 "file:corpus.db?mode=ro"

--- fetch_log : one row per relid attempted (NEVER deleted; audit trail) -------
  relid          INTEGER PRIMARY KEY
  url            TEXT      full URL fetched
  http_status    INTEGER   200 = release exists | 302 = no such record | other
  fetched_at     TEXT      ISO-8601 UTC timestamp
  elapsed_ms     INTEGER   round-trip latency (used to detect server sickness)
  byte_size      INTEGER
  content_sha256 TEXT      integrity hash of the raw page
  parse_status   TEXT      ok | partial | failed | absent
                           ok      = parsed cleanly, row exists in `releases`
                           partial = parsed but a non-critical field missing
                           failed  = structural parse failure (rare)
                           absent  = 302, no release at this relid (a real gap)
  parse_warnings TEXT      JSON array, e.g. ["title_from_heading"]

--- releases : the corpus (one row per successfully parsed release) ------------
  relid          INTEGER PRIMARY KEY  -> fetch_log.relid
  title          TEXT
  heading        TEXT      centred sub-heading; often differs from title
  ministry_raw   TEXT      ministry string exactly as printed on the page
  ministry_id    INTEGER   -> ministries.ministry_id (NOT yet populated; see note)
  release_date   TEXT      ISO-8601 date, e.g. "2025-03-14"  (sortable as text)
  release_time   TEXT      "HH:MM" IST
  body_text      TEXT      full plain-text body of the release
  word_count     INTEGER
  char_count     INTEGER
  image_count    INTEGER   number of embedded images
  image_urls     TEXT      JSON array of image URLs
  has_devanagari INTEGER   1 if Hindi characters present (English corpus; flags
                           mixed-language records — usually a few stray words)
  mojibake_ratio REAL      density of literal "?" runs (flags encoding damage)

--- ministries : controlled vocabulary lifted from PIB's search dropdown -------
  ministry_id    INTEGER PRIMARY KEY   (PIB's own internal id)
  canonical_name TEXT                  e.g. "Prime Minister's Office"
  NOTE: 85 rows. releases.ministry_id is not yet linked to this — a small
  alias-mapping step is pending (ministry_raw has spelling variants like
  "Ministry of Electronics & IT" vs "...Information Technology"). Until then,
  GROUP BY ministry_raw for ministry breakdowns (good enough for exploration).

--- terms : the keyword-expansion vocabulary ----------------------------------
  term         TEXT PRIMARY KEY
  round        INTEGER   0 = seed, 1..n = discovered in that expansion round
  parent_term  TEXT      which term's context surfaced this one (provenance)
  status       TEXT      candidate | accepted | rejected
  reviewed_by  TEXT      "seed" | "human"
  reviewed_at  TEXT
  lift_score, doc_freq, novel_docs, note  -- scoring metadata

--- term_matches : which release each term matched -----------------------------
  term, relid, match_count, first_offset
  NOTE: currently EMPTY. Expansion rounds computed matches in memory and did not
  persist them. Populating this is a pending ~30-min task (see Part E). Until
  then, matches are recomputed on the fly by expand.py.

--- ai_classifications : THE RESEARCH PAYLOAD (empty until classification) ------
  relid, run_id
  is_ai_relevant     INTEGER   0/1
  is_substantive     INTEGER   0/1  (real content vs passing mention)
  mention_type       TEXT      deployment | procurement | pilot | policy |
                               research | training | conference | rhetorical | ...
  lifecycle_stage    TEXT      announced | tendered | piloted | operational | ...
  deploying_body     TEXT      agency/ministry/PSU operating the system
  system_name        TEXT      e.g. "BHASHINI", "MausamGPT", "Divya Drishti"
  application_domain TEXT      agriculture | health | defence | policing | ...
  technology_type    TEXT      ML | NLP | computer_vision | facial_recognition |...
  beneficiary_scale  TEXT      as stated in the release (verbatim)
  budget_mentioned   TEXT      as stated (verbatim)
  evidence_quote     TEXT      verbatim span justifying the classification
  evidence_start/end INTEGER   char offsets into body_text (so every claim is
                               traceable back to the exact sentence)
  confidence         REAL
  run_id -> classification_runs (model_id, prompt_version, prompt_sha256, ...)
  DESIGN INTENT: every classification carries a verbatim quote + char offsets, so
  any finding in the final analysis is auditable back to source. run_id lets you
  re-classify under a revised definition and DIFF runs rather than overwrite.

PART D — USEFUL QUERIES (copy-paste into sqlite3 corpus.db)
--------------------------------------------------------------------------------

# How many releases per year
SELECT substr(release_date,1,4) yr, COUNT(*) FROM releases
WHERE release_date IS NOT NULL GROUP BY yr ORDER BY yr;

# Full-text search the corpus (uses the FTS index)
# CAUTION (corrects an earlier error in this file): releases_fts is an
# EXTERNAL-CONTENT index. It does NOT populate itself. Until it is rebuilt, this
# query silently returns ZERO rows — it does not error. An earlier version of
# this handoff implied this query was verified working; it had been run against
# an empty index. Rebuild the index first, then this query works:
#     INSERT INTO releases_fts(releases_fts) VALUES('rebuild');
SELECT r.relid, r.release_date, r.ministry_raw, r.title
FROM releases_fts f JOIN releases r ON r.relid = f.rowid
WHERE releases_fts MATCH 'artificial intelligence' ORDER BY r.release_date DESC LIMIT 20;

# Read one full release
SELECT title, ministry_raw, release_date, body_text FROM releases WHERE relid = 265600;

# AI-term hits in 2025 (simple LIKE; FTS MATCH is faster for single terms)
SELECT COUNT(*) FROM releases
WHERE release_date LIKE '2025%'
  AND (body_text LIKE '%artificial intelligence%' OR body_text LIKE '% AI %');

# Releases mentioning a specific system
SELECT relid, release_date, title FROM releases
WHERE body_text LIKE '%Bhashini%' ORDER BY release_date;

# Ministry breakdown (use ministry_raw until ministry_id is linked)
SELECT ministry_raw, COUNT(*) n FROM releases GROUP BY ministry_raw ORDER BY n DESC LIMIT 20;

# Where are the gaps? (relids that returned "no such record")
SELECT COUNT(*) FROM fetch_log WHERE parse_status = 'absent';

# The accepted keyword vocabulary
SELECT term, round FROM terms WHERE status='accepted' ORDER BY round, term;

  1. DRONES — is "drone surveillance / counter-drone / drone mapping" in scope
     as AI, or excluded as aerial hardware? (A distribution scheme like "Drone
     Didi" is clearly out either way.)

  3. AUTONOMOUS SYSTEMS — "autonomous vehicle/underwater vehicle" is in; the
     trick is excluding "autonomous institute/body" (a governance term, the

    with no working search and corrupted encoding — deliberately excluded, and
